# 2026-11-06～07 移植记录

[English](./2026-11-06-07.en.md) · 简体中文

时间范围为北京时间 2026-11-06 至 07，覆盖本轮标准 NixOS 启动修复、升级、双系统迁移和外设实测。
以下按因果和实施阶段记录；早期故障归纳来自已有会话、日志及补丁，并非每一步都发生在同一个小时。
当前入口是 [HANDOVER](../HANDOVER.md)，开放事项以 [TODO](../../TODO.md) 为准。

## 1. 起点与路线

设备此前使用 Android，并有 OrangeFox；存储末尾已有旧 Mobile NixOS 的 `linux` 分区。
单系统 NixOS 刷入 `userdata` 后，曾出现 U-Boot → 系统 → 自动重启的循环，之后的诊断构建又表现为黑屏不重启。
用户目标是 U-Boot 启动的标准 NixOS，可以普通 rebuild 更新和回退，不继续旧 Mobile NixOS 的整包 rootfs 路线。

保留原项目板级支持，优先参考 Debian 的内核、固件和厂商服务；没有为了启动故障重写整套 U-Boot，
也没有把 EFI 或迁移 vanilla-mobile-nixos 作为解决启动问题的前置条件。

“单系统”当时描述启动与根分区使用方式，并不表示已经把 Android `super`、旧 `linux` 等分区合并清空。
这也解释了此前空间只显示约半盘，以及后来仍能恢复原 Android 系统内容。

## 2. 建立控制通道，定位启动交接

屏幕 `Starting kernel`、`SHENG handoff: jumping to Linux` 只能定位到交接，不能单独证明 Linux 是否运行。
曾通过 USB 串口读到 NixOS root，但屏幕/USB 状态又使人误以为一直没有进入系统。
后续区分 ABL fastboot、Recovery ADB、U-Boot 菜单、Linux USB gadget 和网络 SSH。

早期试验包括诊断参数、低地址加载、硬件 UART 参数和不初始化 U-Boot 显示的版本。
它们是排障试验，不是当前应继续叠加的修复方案。镜像加载前后 CRC 一致，FDT 检查通过，
说明不能只归因于文件损坏；EL=1 和固定加载地址也不是足以单独确认根因的证据。

### 实际修复：内存来源

U-Boot 内置 DT 记录的是特定 8 GiB 设备的内存/固件保留区，而本机为 16 GiB。
最终使用 ABL 传入并经校验的外部内存范围，避免把内置布局当作所有变体的权威来源。
补丁为 `packages/u-boot/patches/prefer-abl-memory-layout.patch`。
仅保留所需内存修复的正常显示路径也成功进入 NixOS，用户确认了屏幕 root 命令行。

后续再修复菜单“重启 fastboot”：解析 PMIC SDAM reboot-mode，写入并校验后复位，
而不是依赖此前无效的普通 reset/BCB/IMEM 尝试。
补丁为 `packages/u-boot/patches/fix-fastboot-menu-reboot-mode.patch`；已实际进入真正的 ABL fastboot。

U-Boot 源锁从旧引用更新到已存在的 `7025b79` 时，补丁上下文需要调整；
不是原作者突然提交了新代码，也不是两个工作分支发生了 Git 合并冲突。

## 3. 内核与系统升级，证明标准更新链

将内核升级为 7.3.0，内核配置优先采用 Debian 仓库根目录的完整 `sm8550.config`。
同名的内核仓库内 defconfig 片段不能被误当作完整配置。
更新锁定 Nixpkgs，并按 Debian 方案核对 FastRPC、SSC/IIO、THP、笔状态和指纹组件。
保留兼容的 Zig 和指纹补丁基础版本，没有以“最新”为由强行升级所有底层依赖。

早期有本机/设备端构建试验；后续正式产物使用仓库 GitHub ARM CI，核对后再部署到设备。
CI 导出完整系统和内核闭包，减少为一次配置更新重刷 rootfs 的需要，也减少跨分支内核重编。
个人最小样板和 flake-parts 样板完整构建，并与镜像系统路径比较，而不只做语法示例。

在设备上测试候选系统、普通 `nixos-rebuild boot`、重启、回退及返回新版本。
原始 7.2.2 世代曾启动失败，不能把它当作已修好的通用回退项。
随后使用已知可用的不同世代完成回退验证。新双系统的 profile 是另一套，世代号不能跨 rootfs 比较。

### 声卡首启顺序修复

原 UCM unit 只有 `ConditionPathExists`，若异步声卡尚未出现，unit 就会被跳过，
不会在设备后来出现时自动重跑。手动启动能成功，说明不能直接归因于 UCM 内容错误。
添加对 `dev-snd-controlC0.device` 的依赖和顺序后，新的 CI 系统重启测试通过。
后续完成扬声器实听和麦克风电平测试。

### 首次 rebuild 下载源码不等于重新编译内核

新 rootfs 已含运行闭包，但不一定含求值/生成配置时需要的全部源码。
首次 rebuild 曾因下载内核源较慢而等待；本轮复用了已有同内容 store 源路径。
实际运行内核已经存在，不应看到 fetch/配置生成就宣称正在完整编译内核。

## 4. 单/双系统分离实现

没有把默认单系统输出直接改成双系统。新增：

- `nixosConfigurations.sheng-dual`，根分区 `linux`，主机名 `sheng-dual`。
- `nixos-dual` 和 `u-boot-dual`。
- 独立的 `build-dual` 工作流及单独命名的产物。

U-Boot 仍用同一份源码和修复，通过构建参数替换根分区读取及救援参数。
默认 `userdata` 构建不添加多余空 postPatch 属性，避免无意改变原单系统 derivation。
CI 比较单/双系统内核、DTB、固件、关键服务和除 root 以外的参数。

双系统 CI 曾在比较 `hardware.firmware` 时失败：最终 NixOS 选项是合并后的 derivation，不是原始列表。
修复比较脚本后通过，不是双系统内核或 rootfs 无法构建。

## 5. 先验证 linux，再动 userdata

只读审计确认旧 `linux` 是旧 Mobile NixOS 残留。用户明确允许覆盖该内容；没有据此扩大到其他分区。
先擦除并刷写 `linux` 的双系统 CI sparse rootfs，迁入网络配置和测试 SSH 公钥，保留原 `userdata` 单系统。
临时 `fastboot boot` 双系统 U-Boot 后，确认实际根为 `linux`、hostname 为 `sheng-dual`，文件系统自动扩容。

在这套独立系统上完成标准 rebuild、仅增加标记的候选世代、候选启动以及回退原始 CI 世代。
然后备份原 `boot_b`，把已验证的双系统 U-Boot 写入 B 槽，验证永久 B 槽启动和启动成功标记。

原 `userdata` 单系统的完整文件树另外归档，包含权限、ACL、xattr、Nix store/数据库。
先在 `linux` 内保存以避免慢 Wi-Fi 阻塞，再经 Recovery ADB 复制到电脑，双份 SHA256 一致并通过压缩完整性校验。
这是文件级可恢复材料，不是 GPT/整盘镜像；中断的 `.partial` 不能当作备份。

## 6. Android 恢复与 Recovery 槽位

恢复前检查设备原有 `vbmeta_a` 及 `super`，确认原有 Android 内容为 Android 16
`OS3.0.304.0.WNXCNXM`。boot/init/vendor 组件中 Android 13 属性不是整个系统版本。

从小米官方 CDN 的同版本完整 OTA 中分段提取 `boot`、`dtbo`、`init_boot`、`vendor_boot`：

- 核对 payload 分区哈希，并与设备原有 AVB salted hash descriptor 对照。
- 实际只恢复 A 槽这些启动文件，没有重刷完整官方 ROM，没有重刷 `super`。
- 因此启动的系统内容仍是设备原有 ROM；不能宣称已经证明它是全新纯官方系统。
- 用户随后提供 Cream 包目录，只检查了目录；用户取消该路线，最终没有刷入 Cream。

获得用户对清空原 `userdata` 的明确确认后，使用 OrangeFox 的 `format data` 重建 Android F2FS 数据分区及加密状态。
在 B 槽 Recovery 中首次遇到动态分区 merge 状态检查拒绝，没有真正格式化；切回 A 槽 OrangeFox 后完成。
不要绕过检查直接假定文件系统已经重建，应读取日志和实际挂载类型。

切 B 槽后曾看到 TWRP，原因是 A/B 各自有 recovery，B 原先就是旧 TWRP，并非橙狐被代码替换。
用户提供新版 recovery 并要求 B 也用橙狐；备份 B 后刷入指定 OrangeFox，启动 B Recovery 并比较两槽哈希一致。
A 槽原橙狐与用户指定文件相同，之前备份哈希也相同。

## 7. 双系统验收和合并

Android 首次到联网激活界面，之后经 ADB 确认 `sys.boot_completed=1` 和 `device_provisioned=1`。
执行 Android A → NixOS B → Android A → NixOS B：

- Android 初始化状态及测试文件保留。
- NixOS 仍挂载 `linux`，系统路径与 CI 一致，测试文件保留。
- Android 初始化后再次 rebuild 成功，声卡/触摸/传感器等基础服务正常。
- 两槽均标记启动成功，用户确认 NixOS 屏幕正常。

PR #1 合并后重新核对两条 main CI。单系统关键输出与原稳定版本一致，双系统关键输出与实测版本一致。
证据链接、系统路径、内核/DTB/U-Boot 哈希集中在 [HANDOVER](../HANDOVER.md)，不在多处重复维护。

## 8. 外设交互测试

后续记录不只是“节点存在”：

- 多点触摸收到坐标/接触事件，原装键盘收到 8 次 Shift 按下/释放。
  实物是不带触控板版本，内核列出触控板节点不能作为有实物或已经通过的证据。
- ALSA 播放两秒低幅提示音，用户确认听到；麦克风仅在内存采集两秒并计算非零电平，没有保存录音。
- 主摄/前摄分别收到三帧彩色数据；副摄收到原始 Bayer 帧，但去马赛克格式限制仍存在。
- 笔先在 120 Hz 测得坐标/悬停/倾角，但没有压感。进一步定位到未完成蓝牙配对。
  纯命令行无桌面认证代理，Qt 配对助手单独运行仍报 `No agent available`。
  临时注册代理、对侧边读出的准确笔地址配对/信任/连接后，THP 建立 HID report-5 压感通道。
  最终记录到落笔/抬笔、笔按键、倾角与 0～8057 的压力变化。
  结束后恢复 144 Hz，停止发现与临时代理；没有永久修改刷新率配置。
- 指纹完成录入。一次验证等待较久触发 libfprint 防过热保护，不能记为拒绝或通过。
  停止采集冷却后，“预期错误手指”却匹配成功；向用户核实后确认实际用了同一根手指，因此是正确匹配而非误识别。
  再用真正未参与录入的手指得到 `verify-no-match`。
  按用户要求删除测试指纹，并确认 root 无任何残留录入记录；没有导出指纹模板。

这些测试证明的是本轮列出的交互，不是所有桌面应用、所有声道、所有蓝牙重连和所有 Android ROM 的全量验收。

## 9. 最终维护决定

后续重点是用户实际桌面、待机唤醒、续航/充电、配件细节和应用级外设体验。
用户明确表示不需要自动 OTA 保护，接受选择性重刷 Android；不再把 OTA 实现列为必须完成的移植事项。
独立 `linux` 不会阻止整包脚本覆盖 Linux 的 boot 槽，重刷时仍需审查目标分区。

有价值的经验：一次只验证一个假设；先核对实际根分区/系统路径，再判断画面；
先查 Debian 的真实实现，再决定是否独立修复；先证明候选能更新和回退，再迁移唯一可用的数据分区。
